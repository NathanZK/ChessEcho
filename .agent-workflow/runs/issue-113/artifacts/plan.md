It implements provider‑neutral external identity persistence, opaque hashed server sessions with full lifecycle, a provider‑adapter boundary **without selecting or integrating a production provider**, secure cookie‑based request session resolution, the CSRF/credentialed‑origin contract, a minimal current‑session/logout API, an explicit development‑only principal, and the minimal frontend session bootstrap/state. ## 1. Problem understanding

Today a browser‑selected Chess.com username is treated as identity. `GameImportService.getOrCreateAccount(username, platform)` (`src/main/kotlin/com/chessecho/service/GameImportService.kt:207`) silently creates an `AppUser` with a `"$username@placeholder.chessecho.com"` email (`:214‑215`) and a globally unique `ChessAccount(platform, username)`. (Historical: upstream #85 refactored this file for live import progress, and upstream #111 did not touch it at all, so the placeholder‑user creation path remains intact and its anchors `:207`/`:214‑215` are exact at `09fac2b`.) There is no authenticated principal, no session boundary, no CSRF/credentialed‑CORS contract (`AppConfig.corsConfigurer` allows only the two localhost origins with no credentials), and the frontend (`frontend/src/services/api.ts` bare `fetch`, `frontend/src/utils/browserStores.ts` `activeUsernameStore`) treats a `localStorage` username as “Chess.com Connected” (`Header`). The repository has **no** Spring Security dependency and **no** frontend auth SDK (verified: `grep spring-security build.gradle.kts` → none; `frontend/package.json` has no auth package).

This slice builds the durable identity/session substrate that later slices (provider integration, account association, owner‑scoped authorization, #76) depend on, exactly as #79 §7 item 1 (“Identity/session foundation”) defines.

## 2. Scope

### In scope
- **Identity persistence:** `AuthIdentity(app_user_id, issuer, subject, email_snapshot?, email_verified?, …)` unique on `(issuer, subject)`; make `app_user.email` nullable so a provider‑neutral principal can exist without an email.
- **Session persistence & lifecycle:** `AuthSession(token_hash, app_user_id, created/last_seen/idle_expires/absolute_expires/revoked_at)` — creation, hashed‑secret lookup, sliding idle + absolute expiry, revocation, rotation, logout, and a cleanup path for expired/revoked rows.
- **Provider‑adapter boundary:** an interface consuming already‑validated `(issuer, subject)` claims, with **no** production provider chosen; the dev principal is its only wired caller.
- **Request session resolution:** `HttpOnly` opaque session cookie resolved by a servlet filter into a request‑scoped principal; missing/invalid/expired/revoked → fail closed.
- **CSRF + credentialed CORS contract:** double‑submit cookie CSRF for state‑changing session endpoints; credentialed CORS restricted to configured origins.
- **APIs:** `GET /api/me`, `POST /api/logout`, and a dev‑only `POST /api/dev/session`.
- **Frontend:** session bootstrap from `/api/me`, loading/authenticated/unauthenticated‑or‑expired/error states, credentials + CSRF plumbing, logout/expiry clearing of private state with stale‑response protection, no session material in `localStorage`.
- **Development‑only principal:** gated by an explicit development‑profile allowlist (`@Profile("dev","local")`) **and** an opt‑in property (default off), with an always‑registered startup guard that aborts boot if the property is enabled outside the allowlist (including the default/production profile); routed through the same identity/session code path.
- **Docs:** `API_CONTRACT.md` + a new architecture doc for the session contract.

### Out of scope (explicit non‑goals — deferred to follow‑ups)
Chess.com association/management; wholesale owner‑scoped migration of `GameController`/`GameService`/`WeaknessController`/`PuzzleController`/import job ownership; async import ownership/concurrency redesign; legacy placeholder‑data adoption/quarantine; `HumanMoveBfsController` admin role protection; #76 progress; profiles/account‑management/session‑management UI; production provider selection. Existing anonymous username‑based import/read endpoints remain behaviorally unchanged; they are simply not part of the new authenticated boundary.

## 5. Design decisions specific to #113 (with rationale)

These are planner decisions the issue explicitly delegates or that #79 already determines; none is a product/human design decision. Each is a substitutable implementation detail that preserves the #79 contract.

1. **No Spring Security; a lightweight servlet filter instead.** #79 §1 records that the repo has no security framework and leaves framework/provider selection open; §7 item 1 says only “security dependency/configuration.” Adding `spring-boot-starter-security` auto‑configures a filter chain that, by default, secures **every** endpoint and enables CSRF on **all** state‑changing requests (including the existing anonymous `POST /api/games/import` and admin BFS POSTs), which would change endpoint behavior the non‑goals forbid touching. A custom `OncePerRequestFilter` scoped to reading the session cookie plus a double‑submit CSRF check applied only to the new state‑changing endpoints keeps the slice minimal and leaves existing endpoints untouched. If reviewers prefer Spring Security later, it can replace this while preserving the same `/api/me`, `/api/logout`, cookie, and CSRF contract.
2. **CSRF = double‑submit cookie.** The issue says “the selected CSRF contract,” delegating the choice. Double‑submit (non‑`HttpOnly` `XSRF-TOKEN` cookie + `X-XSRF-TOKEN` header) is stateless, SPA‑friendly, and needs no server‑side CSRF store. The session cookie stays `HttpOnly`; the CSRF cookie is deliberately readable and is **not** a session secret.
3. **Cookie attributes are config‑driven; `SameSite=Lax` default works in dev.** For SameSite, “site” is the registrable domain: `localhost:3000` and `localhost:8080` are the **same site** (ports are ignored), so `Lax` cookies are sent on dev cross‑origin requests; CORS+credentials is still required because the *origins* differ. Prod sets `Secure=true` and may use `Lax` same‑site or `None; Secure` cross‑site via config. This satisfies AC4 without a human deployment decision now.
4. **`app_user.email` becomes nullable.** The provider‑neutral boundary must provision an `AppUser` from `(issuer, subject)` claims that may lack email (D1: `email_snapshot?` is optional metadata). Verified that only `AppUserRepository.findByEmail(email: String)` and `GameImportService` (which still passes a non‑null placeholder email) touch `email`; making the column/entity field nullable is safe and is the minimal change honoring D1. The `UNIQUE(email)` constraint is retained (Postgres permits multiple NULLs).
5. **Session durations & cleanup via config + scheduled sweep.** Idle and absolute expiry come from `chessecho.auth.session.*` (defaults: idle 30 min sliding, absolute 30 days). A `@Scheduled` cleanup (project already enables `@EnableScheduling` on `ChessEchoApplication`) deletes revoked/absolutely‑expired rows. Exact production durations remain deployment config, as #79 D2 states.
6. **Principal injection via a `HandlerMethodArgumentResolver`.** Idiomatic Spring MVC without Spring Security; registered through a `WebMvcConfigurer.addArgumentResolvers` (same extension point `AppConfig` already implements).
7. **Dev principal is a fail‑closed profile allowlist, not a prod denylist.** The repository has **no** `prod` Spring profile: production launches on the **default** profile (`Dockerfile` `ENTRYPOINT ["java","-jar","app.jar"]` with no `SPRING_PROFILES_ACTIVE`; `docker-compose.yml` sets only datasource env; grep confirms no `application-prod.yml` and no `@Profile` anywhere in `src/main`). A guard keyed on a `prod` profile would therefore never fire in the real deployment. Instead, the dev path is permitted **only** under an explicit development profile — the allowlist is exactly `{dev, local}` — enforced two ways: (a) `@Profile("dev", "local")` on `DevSessionController`/`DevIdentityProvider` so the default profile can never expose the endpoint (bean absent → `404`), and (b) an always‑registered `DevModeStartupGuard` that aborts boot when `chessecho.auth.dev-mode.enabled=true` and none of `{dev, local}` is active (the default/production profile is not in the allowlist, so it fails closed). This satisfies AC9/#79 D7 ("fails closed outside development") against the repository's actual default‑profile production configuration.
8. **Identity/session mutations are transactional.** `establishSession`, `resolveSession` (it slides `last_seen_at`/`idle_expires_at`, a write), `rotateSession`, `revokeSession`, and `cleanupExpiredSessions` are annotated `@Transactional`. Rotation runs the revoke of the old row and the insert of the new row in **one** transaction, so no committed state ever exposes two live sessions or zero live sessions for the user (atomic swap on commit; see §7).
9. **New `Instant` columns use plain `TIMESTAMP`, matching `app_user`.** V1 maps `Instant` fields against a **mixed** convention — plain `TIMESTAMP` (`app_user`, `chess_account`, `async_job`, `game`) and `TIMESTAMP WITH TIME ZONE` (`position`, `position_occurrence`, `engine_analysis`, `imported_archive`, `user_position_weakness`, `user_position_stats`, `human_move_bfs_seen_game`); both forms currently pass prod `ddl-auto=validate`, so Hibernate's default `Instant` mapping validates against either here. To avoid any divergence and remove the internal contradiction flagged in review, the new `auth_identity`/`auth_session` columns adopt plain `TIMESTAMP`, the same type used by `app_user` — the table these rows reference — with no per‑entity `columnDefinition` override needed (§6.1, §13).

## 6. Proposed changes & affected files

### 6.1 Database — new Flyway migration `V2__identity_and_session.sql`

Additive only; `V1__init.sql` is never edited (matches #79 §5).

```sql
-- Identity: decouple internal identity from email.
ALTER TABLE app_user ALTER COLUMN email DROP NOT NULL;   -- UNIQUE(email) retained; multiple NULLs allowed

CREATE TABLE auth_identity (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    app_user_id    UUID         NOT NULL REFERENCES app_user (id),
    issuer         VARCHAR(255) NOT NULL,
    subject        VARCHAR(255) NOT NULL,
    email_snapshot VARCHAR(255),
    email_verified BOOLEAN,
    created_at     TIMESTAMP NOT NULL DEFAULT now(),
    last_seen_at   TIMESTAMP NOT NULL DEFAULT now(),
    UNIQUE (issuer, subject)
);
CREATE INDEX idx_auth_identity_app_user ON auth_identity (app_user_id);

CREATE TABLE auth_session (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    token_hash         VARCHAR(64)  NOT NULL UNIQUE,   -- SHA-256 hex of opaque secret
    app_user_id        UUID         NOT NULL REFERENCES app_user (id),
    dev_principal      BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at         TIMESTAMP NOT NULL DEFAULT now(),
    last_seen_at       TIMESTAMP NOT NULL DEFAULT now(),
    idle_expires_at    TIMESTAMP NOT NULL,
    absolute_expires_at TIMESTAMP NOT NULL,
    revoked_at         TIMESTAMP
);
CREATE INDEX idx_auth_session_app_user ON auth_session (app_user_id);
CREATE INDEX idx_auth_session_expiry ON auth_session (absolute_expires_at);
```

**Column‑type convention (verified):** the new `Instant`‑backed columns are declared as plain `TIMESTAMP` to match `app_user.created_at` — the table these rows reference — and the other plain‑`TIMESTAMP` V1 tables (`chess_account`, `async_job`, `game`). V1 is mixed (some tables use `TIMESTAMP WITH TIME ZONE`) and both forms already pass prod `ddl-auto=validate` against Hibernate's default `Instant` mapping, so no per‑entity `columnDefinition` override is required; plain `TIMESTAMP` is the conservative, contradiction‑free choice (§5.9, §13).

**Testing‑gap note (carried from #79 §8):** `application-test.yml` disables Flyway and uses H2 `create-drop`, so the V2 SQL DDL itself is not exercised by the JVM suite; H2 builds the schema from the JPA entities. This gap is about the DDL text and constraints, **not** the timestamp type: the entity `Instant` fields are the source of truth Hibernate validates against in prod, and plain `TIMESTAMP` matches the existing validated `app_user` mapping. To keep constraints test‑reachable, the entities express `UNIQUE(issuer, subject)` and `token_hash UNIQUE` via JPA (`@Table(uniqueConstraints=…)`/`@Column(unique=true)`) so `@DataJpaTest`/H2 enforces them. PostgreSQL‑only migration proof remains a documented follow‑up obligation (§12), not a claim of this slice.

### 6.2 Backend — new/changed Kotlin

**Domain (`com.chessecho.domain`)**
- `AppUser.kt` — change `val email: String` → `val email: String?` (nullable), keep `@Column(nullable = true, unique = true)`; other fields unchanged.
- New `AuthIdentity.kt` — `id`, `@ManyToOne AppUser` (JoinColumn `app_user_id`), `issuer`, `subject`, `emailSnapshot: String?`, `emailVerified: Boolean?`, `createdAt`, `lastSeenAt`; `@Table(uniqueConstraints=[UniqueConstraint(columnNames=["issuer","subject"])])`.
- New `AuthSession.kt` — `id`, `tokenHash: String` (`@Column(unique=true)`), `@ManyToOne AppUser`, `devPrincipal: Boolean`, `createdAt`, `lastSeenAt`, `var idleExpiresAt`, `var absoluteExpiresAt`, `var revokedAt: Instant?`.

**Repositories (`com.chessecho.repository`)**
- New `AuthIdentityRepository : JpaRepository<AuthIdentity, UUID>` — `findByIssuerAndSubject(issuer, subject): AuthIdentity?`.
- New `AuthSessionRepository : JpaRepository<AuthSession, UUID>` — `findByTokenHash(tokenHash): AuthSession?`; `deleteByRevokedAtIsNotNullOrAbsoluteExpiresAtBefore(cutoff: Instant)` (or a `@Modifying @Query` cleanup) for the sweep.

**Provider‑adapter boundary & services (`com.chessecho.service.auth` new package)**
- `VerifiedIdentityClaims(issuer: String, subject: String, emailSnapshot: String?, emailVerified: Boolean?)` — already‑validated claims value type.
- `IdentityProviderAdapter` interface — `fun claims(request): VerifiedIdentityClaims` boundary (documented; **no production implementation** wired). Independently testable.
- `SessionSecret` util — `SecureRandom` 32‑byte secret, base64url encode; `sha256Hex(secret)` hashing.
- `IdentitySessionService` — core provider‑neutral service (all mutating methods `@Transactional`, §5.8):
  - `@Transactional establishSession(claims: VerifiedIdentityClaims, devPrincipal: Boolean): EstablishedSession` → resolve/provision `AuthIdentity` (+ `AppUser` if absent) by `(issuer, subject)`, update `last_seen_at`/`email_snapshot`, create `AuthSession` (hash stored), return raw secret + expiries (raw secret returned only for the cookie writer, never persisted/logged). Provisioning + session insert commit together.
  - `@Transactional resolveSession(rawSecret: String): AuthenticatedPrincipal?` → hash, load by `token_hash`, reject if `revoked_at != null` or now ≥ idle/absolute expiry, else slide `idle_expires_at`/`last_seen_at`, return principal. It is `@Transactional` (not read‑only) because the idle slide is a write.
  - `@Transactional rotateSession(rawSecret): EstablishedSession` → within one transaction, set the old row's `revoked_at=now` and insert a new `AuthSession` for the same user; the new secret is returned to the caller only after commit. Atomicity: revoke + insert commit or roll back together, so no committed state ever shows two live sessions or zero for the user, and a rollback leaves the original session intact (§7).
  - `@Transactional revokeSession(rawSecret)` → set `revoked_at` (idempotent; a second call is a no‑op).
  - `@Transactional cleanupExpiredSessions()` → `@Scheduled` sweep.
- `AuthenticatedPrincipal(appUserId: UUID, devPrincipal: Boolean)`; `EstablishedSession(rawSecret, idleExpiresAt, absoluteExpiresAt, principal)`. **The principal deliberately carries no raw secret and no session id.**
- `DevIdentityProvider` — supplies fixed dev claims (`issuer="dev-local"`, `subject="local-dev"`); gated on `@Profile("dev", "local")` + `@ConditionalOnProperty("chessecho.auth.dev-mode.enabled", havingValue="true")` so it exists only inside the development allowlist (§5.7).

**Web/security plumbing (`com.chessecho.config` / `com.chessecho.web`)**
- `SessionCookieProperties` `@ConfigurationProperties("chessecho.auth")` — `cookie.name` (`CHESSECHO_SESSION`), `cookie.secure`, `cookie.sameSite` (`Lax`), `cookie.path` (`/`), `csrf.cookieName` (`XSRF-TOKEN`), `csrf.headerName` (`X-XSRF-TOKEN`), `session.idleTimeout`, `session.absoluteTimeout`, `devMode.enabled` (default false). Registered by appending `SessionCookieProperties::class` to `AppConfig`'s existing `@EnableConfigurationProperties(ChessPubApiProperties::class, PracticalEvidenceProperties::class)` list — the `PracticalEvidenceProperties` entry is upstream #111 baseline and is retained, not replaced.
- `SessionAuthenticationFilter : OncePerRequestFilter` (`@Component`, auto‑registered) — read session cookie, `resolveSession`, set request attribute `AuthenticatedPrincipal`; ensure `XSRF-TOKEN` cookie exists on the response (issue if absent); always clear per‑request state in `finally`. Does not itself reject; authorization is enforced where a principal is required.
- `CsrfEnforcement` — a small filter or interceptor applied to `POST /api/logout` and `POST /api/dev/session` requiring the `X-XSRF-TOKEN` header to equal the `XSRF-TOKEN` cookie, compared with a **constant‑time** check (`java.security.MessageDigest.isEqual(header.toByteArray(Charsets.UTF_8), cookie.toByteArray(Charsets.UTF_8))`) as defense‑in‑depth; missing/mismatched → `403 CSRF_FAILED`.
- `AuthenticatedPrincipalArgumentResolver : HandlerMethodArgumentResolver` — inject `AuthenticatedPrincipal` (or throw `UnauthenticatedException` when required and absent). It never exposes the raw session secret.
- `SessionCookieWriter` — builds the session `Set-Cookie` (`HttpOnly`, `Secure`/`SameSite`/`Path` from properties, `Max-Age` from absolute timeout) and the clear‑cookie on logout that **replays the identical `Name`/`Path`/`Secure`/`SameSite`/`HttpOnly` attributes with an empty value and `Max-Age=0`** so browsers actually delete the cookie (a `Set-Cookie` whose attributes differ from the original is not treated as the same cookie).
- `AppConfig.corsConfigurer` — add `.allowCredentials(true)` (the origin list is already explicit `http://localhost:3000`,`http://127.0.0.1:3000`) and **replace `allowedHeaders("*")` with an explicit list** including `X-XSRF-TOKEN` and `Content-Type`. Rationale (corrected): the hard CORS rule is that credentials cannot be combined with a wildcard **origin** — already satisfied by the explicit origins. Spring MVC does *reflect* requested headers rather than emitting a literal `*`, so `allowedHeaders("*")` would technically still function with credentials; we enumerate explicit headers deliberately for clarity and to avoid relying on reflection, not because it is required to make CORS work. Methods are unchanged; formatters are unchanged. This `corsConfigurer` body edit plus the `SessionCookieProperties::class` property‑list addition (above) are the only #113 changes to `AppConfig.kt`; upstream #111 already modified this file by adding `PracticalEvidenceProperties::class` to `@EnableConfigurationProperties`, and the reconciled working copy retains both existing entries, so the `corsConfigurer` body is the sole behavioral change and no upstream registration is lost.
- New `@Configuration SessionWebConfig : WebMvcConfigurer` — register the argument resolver (kept separate from `AppConfig` to avoid overloading it).
- `DevModeStartupGuard` (`@Component` implementing `ApplicationRunner`, **always registered**, not profile‑ or property‑conditional) — reads the active profiles from the injected `Environment` and the `chessecho.auth.dev-mode.enabled` flag; if the flag is true and **none** of the allowlisted development profiles `{dev, local}` is active (i.e. the default/production profile, matching the repository's real deployment), it throws `IllegalStateException` to abort boot. Because it is unconditional, it fires under the default profile; the `@Profile` gate on the dev beans and this guard together make the dev path a true fail‑closed allowlist (§5.7).

**Controllers (`com.chessecho.controller`)**

## 7. Data & control flow

**Bootstrap:** browser `GET /api/me` (credentials) → `SessionAuthenticationFilter` resolves cookie → principal present → `200 CurrentUserResponse`; absent/expired/revoked → `401`. Frontend maps to authenticated / unauthenticated‑or‑expired; network/5xx → error. During `loading`, no personalized request is issued.

**Dev sign‑in (dev only):** `POST /api/dev/session` (CSRF header) → `IdentitySessionService.establishSession(dev claims, devPrincipal=true)` → provision/lookup `AuthIdentity('dev-local','local-dev')` + `AppUser` → new `AuthSession` (hash persisted) → `Set-Cookie` session (raw secret) → `200`. Subsequent `/api/me` returns authenticated.

**Session resolution per request:** cookie secret → SHA‑256 → `AuthSessionRepository.findByTokenHash` → validate `revoked_at`/idle/absolute → slide idle expiry → `AuthenticatedPrincipal`.

**Logout:** `POST /api/logout` (CSRF) → controller reads the raw secret from the session cookie via `@CookieValue` → `revokeSession(secret)` (`@Transactional`, sets `revoked_at=now`, idempotent) → `SessionCookieWriter` clear‑cookie replaying the same `Path`/`Secure`/`SameSite`/`HttpOnly` with `Max-Age=0` → `204`. Next `/api/me` → `401`. Frontend clears private state + invalidates in‑flight generations.

**Rotation:** `rotateSession` runs in **one** `@Transactional` boundary — it sets the current row's `revoked_at=now` and inserts a new `AuthSession` for the same `AppUser`, then returns the new secret/cookie only after commit. Because both writes commit or roll back together, there is never a committed window with two live sessions or zero for the user; a rollback leaves the original session live and usable. `token_hash UNIQUE` prevents a duplicate active secret. Supports sign‑in/privilege‑change rotation; exercised by tests. No production caller beyond the tested service path in this slice.

**Cleanup:** `@Scheduled cleanupExpiredSessions()` deletes revoked/absolutely‑expired rows.

## 10. Edge cases, concurrency & lifecycle

- **Fail‑closed resolution:** any cookie that does not hash to a live, unrevoked, unexpired `AuthSession` yields no principal → `401`; never a partial/authenticated state.
- **No secret leakage:** raw secret exists only in the `Set-Cookie` value; never in a response body, log line, or `localStorage`; DB stores only the SHA‑256 hex.
- **Rotation/revocation race:** `revokeSession` and `rotateSession` run inside a single `@Transactional` boundary; rotation's revoke‑old + insert‑new commit atomically (never a committed window with two or zero live sessions for the user; rollback preserves the original session). `token_hash UNIQUE` prevents duplicate active secrets; resolution re‑reads state each request so a revoked session fails immediately on the next call.
- **CSRF:** double‑submit compares the `X-XSRF-TOKEN` header to the `XSRF-TOKEN` cookie with a **constant‑time** `MessageDigest.isEqual` byte comparison (defense‑in‑depth); the `HttpOnly` session cookie is never used as the CSRF token; safe methods (`GET /api/me`) are exempt and also seed the `XSRF-TOKEN` cookie so the SPA can perform a subsequent `POST`.
- **Dev principal isolation:** a fail‑closed **allowlist** — the dev bean exists only under `@Profile("dev", "local")` + `@ConditionalOnProperty` (default off), so the default/production profile can never expose it (`404`), and `DevModeStartupGuard` aborts boot if `dev-mode.enabled=true` outside `{dev, local}` (including the default profile). It routes through the same `IdentitySessionService`; `dev_principal` is recorded but grants no extra privilege in this slice.
- **Frontend stale‑response/logout:** reuse the proven monotonic generation guards (`puzzleLoadSeqRef`, `WeaknessesList.loadSeqRef`) — bump generations *before* clearing rendered data so a late resolve/reject is dropped; bootstrap effect uses an in‑flight/unmount guard so a late `/api/me` resolve after unmount is ignored.
- **Same‑site/CORS:** credentialed CORS is bound to the explicit origin list (the hard rule is no wildcard **origin** with credentials — satisfied). Allowed headers are enumerated explicitly (`X-XSRF-TOKEN`, `Content-Type`) for clarity rather than out of necessity — Spring MVC would reflect requested headers even with a `"*"` header pattern under credentials. Dev origins are same *site* so `Lax` cookies are delivered.
- **Cookie deletion:** the logout clear‑cookie replays the identical `Name`/`Path`/`Secure`/`SameSite`/`HttpOnly` attributes with `Max-Age=0` and an empty value, which is what browsers require to actually delete the session cookie.
- **Email nullability:** provisioning without email is valid; the retained `UNIQUE(email)` tolerates multiple NULLs in Postgres; H2 `MODE=PostgreSQL` matches for tests.
